# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A personal, local-only peptide research tracker for two subjects (household members) with different peptides/schedules: inventory + reconstitution math, per-subject dosing protocols (including multi-peptide blends like "KLOW"), a printable calendar schedule, printable vial labels sized for a NIIMBOT M2 label printer, and a consumption report broken down by substance. No accounts, no cloud, no external services. Built deliberately minimal after an earlier full-webapp attempt proved to be too much overhead.

## Running it

There is no build step, no package manager, and no dependencies (JS is plain `<script>` tags, not ES modules, so it also works when opened directly via `file://`).

- **Recommended**: double-click `start.command` (macOS). It runs `server.py` and opens `http://localhost:8765` in the default browser. Leave the terminal window open; closing it / Ctrl+C stops the server.
- **Equivalent manually**: `python3 server.py` from this directory, then open `http://localhost:8765`.
- **No-server fallback**: open `index.html` directly in a browser. Everything still works except data is stored only in that browser's localStorage (see Persistence below).

There is no lint/test/build tooling in this repo — it's plain HTML/CSS/JS + one stdlib-only Python file. Verify changes by opening the app in a browser and exercising the flow (add a peptide/lot/protocol, check Dashboard math, preview Print Schedule and Labels, reload to confirm persistence).

## Architecture

### Files
- `index.html` — app shell: tab nav + one empty container `<div>` per tab, plus three hidden `#printScheduleArea` / `#printLabelsArea` / `#printReportArea` divs that are only populated right before printing.
- `calc.js` — pure dosing/inventory math (`Calc.*`), no DOM access. Concentration, draw volume, syringe units, weekly usage, `projectSupply()` (doses-left/run-out simulation), `isDueOn(protocol, date)` which is the single source of truth for "is this protocol active on this calendar day," and the blend helpers `blendTotalMg()`/`blendComponentDoses()`.
- `app.js` — everything else: state load/save, all seven tab renderers, event binding, print orchestration, server sync.
- `styles.css` — screen styles, including an on-screen `.label-box` sized in real mm so the label preview shows true-to-size before printing.
- `print.css` (loaded with `media="print"`) — print-only rules, keyed off `body[data-print-mode]` (see Printing below).
- `server.py` — stdlib-only HTTP server: serves the static files, exposes `GET/POST /api/data` backed by `data.json`, and `POST /api/labels` to write exported label PNGs to a folder on disk (see NIIMBOT below).
- `data.json` — created automatically on first server connection; the persisted app state when running via the server.
- `start.command` — double-clickable launcher (backgrounds a 1s-delayed `open` of the URL, then runs the server in the foreground).

### State model
The entire app state is one JSON object (see `defaultState()` in `app.js`):
```
{ subjects: [{id, name, color}],
  peptides: [{id, name, notes, isBlend, halfLifeHours: number|null,
              components: [{id, name, mgPerVial, halfLifeHours: number|null}]}],
  inventoryLots: [{id, peptideId, mgPerVial, vials, dateAcquired}],
  protocols: [{id, subjectId, peptideId, vialMgAssumed, bacWaterMl,
               frequency: 'daily'|'eod'|'weekly'|'asNeeded', daysOfWeek: [0-6],
               timeOfDay: ''|'morning'|'evening', endDate: ''|'YYYY-MM-DD',
               cycleOnWeeks: number|null, cycleOffWeeks: number|null,
               doseSchedule: [{id, startDate, doseMg}], active}],
  doseLogs: [{id, protocolId, subjectId, peptideId, doseMg, date, takenAt, note}],
  settings: { labelWidthMm, labelHeightMm, labelExportDpi,
              syringeUnits: 'U100'|'U40', logoDataUrl } }
```
`inventoryLots` is append-only restock history (each vial batch) — gross mg ever acquired for a peptide is `Calc.totalMgOnHand(lots)`, never stored directly. `protocols.vialMgAssumed`/`bacWaterMl` capture the reconstitution assumption used for that protocol's draw-volume math; they're independent of whatever lot mg/vial is actually on hand, so a protocol keeps working even across restocks with different vial sizes. Dose is stored in **mg** (not mcg) throughout; `migrateState()` in `app.js` upconverts any pre-mg data that still has the old `doseMcg` field (divides by 1000) the first time it's loaded.

A peptide can optionally be a **blend** — a single vial with multiple peptides mixed at a fixed ratio (e.g. a "KLOW" blend of GHK-Cu/KPV/BPC-157/TB-500). `isBlend`/`components` capture that fixed recipe; `Calc.blendTotalMg(peptide)` sums it to the vial's total mg (what a blend protocol's `vialMgAssumed` should equal), and `Calc.blendComponentDoses(peptide, doseMg)` splits any dose proportionally by that ratio. Everywhere else in the app — reconstitution math, `inventoryLots`, protocols, `doseLogs` — is completely unaware of blends, since a blend vial is drawn, dosed, and logged exactly like a single-peptide vial; that's physically what's mixed inside it. Only the display layer additionally shows the per-component split: `blendCompositionText()` renders the fixed recipe (used in Inventory, where the vial's contents don't depend on any dose), while `blendBreakdownText()` renders a specific dose's split (used in Protocols/Dashboard/Schedule, where titration means the mg drawn varies by date) — both computed on demand from `peptide.components`, never stored, so editing a blend's recipe later doesn't require touching any protocol or log. Blends are deliberately **not** shown on printed labels — the default 40×20mm label stock has no room for a component list without clipping or colliding with the time-of-day text in the corner; the recipe is only ever shown on-screen in Inventory.

`halfLifeHours` (optional, hours) exists on a non-blend peptide and, separately, on each blend component (`peptide.components[i].halfLifeHours`) — a blend's components generally decay at different rates, so a single half-life on the blend as a whole would be wrong. It powers only the Dashboard's Levels graph (see below); nothing else in the app reads it, and leaving it unset is the honest default for a peptide with no real half-life data, not a validation error.

There's no single flat `doseMg` on a protocol — dose lives in `doseSchedule`, a list of `{startDate, doseMg}` phases sorted ascending, so a protocol can titrate (e.g. 3mg from Jul 1, 5mg from Aug 15) without needing a second protocol. `Calc.doseMgOnDate(protocol, date)` resolves the dose in effect on any given date (the latest phase whose `startDate` has passed); `Calc.protocolStartDate(protocol)` is just `doseSchedule[0].startDate` — the protocol's overall start is implicit in its first phase, not a separate field. `endDate` (optional) stops the protocol being due after that date, independent of the `active` pause/resume flag. `timeOfDay` is a coarse `morning`/`evening`/unset enum, not a specific clock time — deliberately, since the printed schedule only needs "AM or PM" and the exact time isn't needed for the vial math. `migrateState()` also converts old flat `doseMg`+`startDate` protocols into a single-phase `doseSchedule`, and old `HH:MM` `timeOfDay` strings into `morning`/`evening` by comparing the hour to noon. Every place that needs "the" dose for a protocol (Dashboard, printed Schedule, Labels) must look it up for a specific date via `Calc.doseMgOnDate` — there is deliberately no shortcut flat field to read instead, so titration can never go stale in one display but not another.

`frequency: 'asNeeded'` is for PRN-style dosing with no fixed schedule (e.g. bremelanotide-style use) — `Calc.isDueOn()` always returns `false` for it, so it never appears in the Dashboard/printed Schedule's due-today list and never drives `projectSupply()`'s day-walk. Instead the Dashboard's "As-needed" section and the Protocols tab both show a "Log dose" button (`logAdHocDose()` in `app.js`) that pushes a `doseLogs` entry for right now directly — the only doseLogs writer other than `toggleDoseTaken()`/the manual-adjustment form that still sets a real `protocolId`, since an as-needed dose *did* come from a specific protocol, it just wasn't on a predictable day.

`cycleOnWeeks`/`cycleOffWeeks` (both optional, only meaningful together) make a protocol cycle on and off indefinitely — e.g. 8 weeks on, 4 off, repeating forever from `protocolStartDate` — computed inside `Calc.isDueOn()` via `diffDays % ((on+off)*7)` before the frequency switch runs, so off-weeks never reach the daily/eod/weekly check. `endDate` still works independently as a hard outer stop on top of the repeating pattern, for "cycle like this until it's over for good." The Protocols tab's "Cycle length (weeks)" field is a convenience that, when no off-weeks value is given, just computes `endDate` for you (a one-time cycle) instead of setting `cycleOnWeeks` — see the `save-protocol` submit handler in `app.js`. `Calc.dosesPerWeek()` averages down by the on/(on+off) duty cycle so "weekly usage" figures don't overstate consumption during off-weeks; `Calc.projectSupply()` needed no change at all, since it already walks day-by-day through `isDueOn()`.

Each dose-schedule row in the Add/Edit protocol form also shows an "or dose (units)" field next to the mg field, letting a known syringe-draw amount (e.g. "I want 10u") be entered instead of hand-computing mg. `doseMg` is still the only value ever persisted — the units field is a pure UI convenience computed live from that row's mg plus the concentration implied by the form's own `vialMgAssumed`/`bacWaterMl` fields (`Calc.doseMgFromUnits()` is the mg-from-units inverse of `concentrationMgPerMl`/`drawVolumeMl`/`syringeUnits`). Typing in the units field overwrites that row's mg field (one-way); typing in mg, or changing vial size/bac water, just redisplays the equivalent units — mg is never overwritten by anything except a direct edit or the units field. See `protocolFormConcentration()`/`refreshRowUnits()` in `app.js`.

`doseLogs` is the per-dose confirmation log: checking a dose off (Dashboard's Day/Week/Month "Upcoming doses" list, or the on-screen Schedule preview — both call `toggleDoseTaken()`) appends/removes an entry with a snapshot of `doseMg` (looked up via `Calc.doseMgOnDate` for the date being checked) at the time it was taken, so titration changes or edits to the protocol later don't retroactively change historical consumption. `peptideStats()` nets logged consumption against gross acquired stock (`Calc.totalMgConsumed(logs)` subtracted from `Calc.totalMgOnHand(lots)`) to get the actual mg on hand. The printed schedule's checkbox squares are static (paper has no way to write back), but they're pre-filled solid if a dose was already logged before printing — there's still no "scan the printed page" flow, only the on-screen checklist feeds the log.

`peptideStats()`'s "doses left"/run-out figures come from `Calc.projectSupply(netMg, activeProtocols)`, which walks the *actual* schedule forward day by day (via `isDueOn` + `doseMgOnDate`, so titration is exact, not averaged) consuming mg from `netMg`, rather than dividing by an average weekly rate. This matters because a protocol's `endDate` (a cycle) makes dosing stop before stock necessarily runs out — the simulation returns `limitedBy: 'schedule'` in that case, with `scheduleEndDate` and the mg that will be left over once the cycle ends, instead of `limitedBy: 'stock'` with a `stockOutDate` misleadingly projected as if dosing continued forever at the current rate past the cycle's end. `stockPill()` and the Inventory/Dashboard views branch on `limitedBy` to show "cycle ends in Nd" (always ok-colored — a cycle ending isn't a restock emergency) instead of the danger/warn/ok thresholds used for an actual stock-out.

`protocolId` is nullable: entries created by `toggleDoseTaken()` always carry the protocol they came from, but the Inventory tab's per-peptide "manual stock adjustment" form (`add-manual-log` in `renderInventory()`) pushes a `protocolId: null` entry directly, for consumption (or corrections) that never went through a protocol's schedule — e.g. backfilling a dose taken before the app existed. `doseMg` on a manual entry follows the same sign as a normal dose log (positive = taken, subtracts from on-hand mg); it can also be negative, which nets *against* consumption (i.e. adds back to on-hand mg) for correcting an overcount, without needing a second `inventoryLots` row. `isDoseTaken`/`toggleDoseTaken` only ever match on a specific `protocolId`, so manual entries never interact with the interactive/printed schedule checkboxes — they only affect `peptideStats()`'s on-hand math. The optional `note` field (manual entries only) is free text shown next to the entry in the Inventory tab.

Each restock lot's per-vial "remaining (approx)" figure and its +/- buttons (`stepLotVial()` in `app.js`) are the same manual-adjustment mechanism wearing a friendlier UI, not a second inventory ledger: `Calc.lotsRemaining(lots, consumedMg)` attributes a peptide's aggregate `consumedMg` back to individual lots, oldest `dateAcquired` first (FIFO), purely for display — clicking +/- pushes a `protocolId: null` doseLogs entry sized to that specific lot's `mgPerVial`, tagged with a note identifying it as a vial-count adjustment. Because it's FIFO-derived rather than a real per-lot counter, correcting a *newer* lot specifically only lands correctly if older lots are already used up first; out-of-order consumption across differently-priced lots is a known, accepted approximation rather than something the schema tracks precisely.

### Levels graph
The Dashboard's "Levels" card is a relative "how much is still in the system" estimate, built entirely from `halfLifeHours` and mono-exponential decay — `Calc.decayAt(doseMg, hoursSinceDose, halfLifeHours)` is a single dose's remaining amount, and `Calc.levelsOverTime()` sums that (superposition) across every dose event at each sampled hour. This is deliberately **not** a real pharmacokinetic model — no absorption phase, volume of distribution, or bioavailability data exists anywhere in this app, so it says so in the card's own footer text rather than implying more precision than it has.

`doseEventsForComponent()` (`app.js`) builds the dose-event list for one subject+peptide (or one blend component, via `Calc.blendComponentDoses()`) over a fixed ±14-day window: history comes from `doseLogs.takenAt` (the real timestamp a dose was logged), and anything from today onward that hasn't been logged yet is filled in from the active schedule (`Calc.isDueOn`/`doseMgOnDate`), placed at an assumed clock hour from `timeOfDay` (`TIME_OF_DAY_HOUR`, defaulting to noon if unset) — so the curve continues past "now" instead of just stopping. `isDoseTaken()` is checked in that scheduled loop specifically to avoid double-counting a day that's already been logged. `buildLevelsChartSVG()` renders the result as a hand-built inline SVG (no charting library) — a color per component/peptide, weekly gridlines, and a dashed "now" marker.

### Config-upload onboarding
Settings → "Set up from a config file" is an alternative to clicking through the Inventory/Protocols forms one at a time: a friendlier JSON format that references subjects and peptides **by name** rather than internal ids (see `sampleConfigJSON()` in `app.js` for the exact shape, and the Settings tab's "Download example file" button, which generates that same sample for a user to edit). `translateConfig(raw)` in `app.js` validates it and resolves names to freshly-generated ids, returning either `{ ok: false, errors: [...] }` — one specific message per bad row, since a silently-defaulted bad value would be far harder to notice once baked into a whole peptide library — or `{ ok: true, state, summary }`. The translated `state` is held in the module-level `configImportPreview` and shown as a summary card ("2 subjects, 5 peptides...") requiring an explicit "Import and replace" click before it overwrites anything; confirming it goes through the same `migrateState(mergeWithDefaults(...))` path as the Backup importer. It always fully replaces state — there's no merge-with-existing-data mode — since it's meant for setting up a new install, not incrementally editing one that's already in use.

### Persistence (dual-mode, decided at runtime)
`app.js` always reads/writes `localStorage` synchronously first (so the UI never has to wait). On load it also calls `trySyncFromServer()`, which `fetch`es `/api/data`:
- If that succeeds, `data.json` becomes the source of truth from then on — the fetched state overwrites in-memory `state`, and every `saveState()` afterward both writes localStorage *and* POSTs to `/api/data`. If `data.json` doesn't exist yet, the current (localStorage-derived) state is POSTed immediately, migrating it into the file.
- If the fetch fails (e.g. opened via plain `file://`, or the server isn't running), `serverAvailable` stays `false` and the app silently behaves as pure localStorage-only.

The header's `#storageStatus` badge and the Settings → Backup copy both branch on `serverAvailable` to tell the user which mode is active — check both if you change this logic, since they're the only user-visible signal of which persistence mode is live. `serverAvailable` also gates the label-export destination (`labelSaveMode()`, see NIIMBOT below).

All three entry points that load a saved state — `loadState()`, `trySyncFromServer()`, and the Settings → Backup importer — go through `mergeWithDefaults()`. It exists because the obvious `Object.assign(defaultState(), parsed)` replaces the whole `settings` object with the saved one, so any key added to `defaultState().settings` after that save comes back `undefined` rather than taking its default; `settings` needs its own second merge on top. Add a setting without it and the app silently sees `undefined` for every existing user until they touch that field.

### Rendering pattern
No framework, no virtual DOM. Each tab has a `render*()` function that rebuilds its container's `innerHTML` from scratch from the global `state`, then re-attaches event listeners to the fresh elements (listeners don't survive `innerHTML` reassignment, so every render re-binds them). `renderAll()` re-renders every tab and is called after essentially every mutation and on every tab switch — state is small (one household, a handful of peptides/protocols) so this is cheap and intentionally avoids diffing complexity. Module-level UI-only variables (`editingProtocol`, `labelSelections`, `scheduleView`, `dashboardView`, `reportView`, `editingPeptideId`) track transient view state that isn't persisted. `protocolFormDraft` (subjectId -> in-progress `{peptideId, vialMgAssumed, bacWaterMl, frequency, daysOfWeek, timeOfDay, endDate, active, doseRows}`) and `peptideFormDraft` (form key `'new'` or a peptide id -> in-progress `{isBlend, components}` rows) are the odd ones out: each holds an open form's full not-yet-saved state across events that trigger a re-render of their tab. `protocolFormDraft` in particular is kept continuously up to date by a delegated `input`/`change` listener on the whole form (`syncProtocolFormDraft()`), not just at specific button clicks — this is what lets the Add/Edit protocol form survive `switchTab`'s `renderAll()` (previously, navigating away and back reset the form to defaults, since only the dose-schedule rows were preserved). `syncBlendDraftFromForm()` plays the equivalent role for the peptide form. These are the places in the app where a mutation-then-full-rerender needs to preserve not-yet-submitted form state.

### Printing (schedules, labels, and reports)
All three print paths share one mechanism: JS injects the print HTML into a normally-hidden container (`#printScheduleArea`, `#printLabelsArea`, or `#printReportArea`), sets `document.body.dataset.printMode` to `'schedule'`, `'labels'`, or `'report'`, then calls `window.print()`; an `afterprint` listener clears the attribute. `print.css` shows only the matching container during print and hides everything else via `.no-print`.

Schedule and Labels need different physical page sizes, which is why `@page` can't just live in `print.css` as one static rule (Reports doesn't — see below, it just uses the default like Schedule):
- **Schedule** uses the default `@page` in `print.css` (portrait, normal margins, standard letter/A4). `buildScheduleHTML(interactive)` renders a **day-list**, not a grid, via the shared `doseListBlocksHTML()` helper: every dose is its own full-width row grouped under a day heading, so a day with 5-6+ peptides never gets cramped the way a fixed-height calendar cell would — the tradeoff is a month view can span multiple printed pages. Days with zero due doses are skipped entirely.

The whole schedule is wrapped in a single-column `<table class="sched-table">` for one reason: a browser repeats a table's `<thead>` at the top of every printed page, so a multi-page month keeps its title/subject/date on page 3 instead of starting mid-list with no context — and each day is its own `<tr>` so a page break falls between days, never through one. That's why `doseListBlocksHTML()` takes `asTableRows` (the Dashboard, which needs none of this, takes plain divs). There is no way to say "(continued)" on the repeated header without real paged-media support, which browsers don't have.

A month view additionally gets `scheduleTotalsHTML()` appended: per-substance mg for that month next to the trailing 3-month figure, with dose counts. These are **schedule-derived** (`scheduledSubstanceTotals()` walks `isDueOn`/`doseMgOnDate` over the dates), not log-derived like the Reports tab — the appendix hangs off a forward-looking checklist, where the useful number is what's about to be needed for a reorder, not what's already been ticked. It buckets by substance name and splits blends exactly the way `consumptionReport()` does, so the two read consistently; if it should ever show *logged* consumption instead, swapping in `consumptionReport()` over the same date window is the whole change.

Within a day the rows are a four-column grid — checkbox | time of day | peptide | dose — not one run-on sentence, so the doses form a column you can scan straight down; the blend breakdown and the Dashboard's mL/units hang as secondary lines under the peptide and dose cells respectively, keeping the columns intact. Rows are ordered morning → unspecified → evening (`sortedDoseEntries()`), the order the day is actually worked through. Whose dose it is comes from grouping rather than from a name on every row: a day involving one subject names them once in the day heading (`.sched-day-subject`), and only a day that mixes both splits into `.sched-subject-header` groups. `dayLabel()` always includes the real date — "Today" alone means nothing on a page that's been on the fridge for three days — and for `interactive=false` the subtitle adds the dose count and the print date, since a printout has no other way to say how current it is. Note `styles.css` has no `media` attribute, so it applies to printing too and `print.css` only overrides what needs to differ; a screen-only colour (`var(--muted)` on the day heading, for one) will otherwise silently become the printed colour. `interactive=true` (the on-screen preview in `#scheduleContent`) renders real checkbox inputs wired to `toggleDoseTaken()`; `interactive=false` (the print path) renders static squares, pre-filled if already logged. The Dashboard's "Upcoming doses" Day/Week/Month view (`datesForDashboardView()`, always anchored on today rather than a user-pickable anchor date) calls the same `doseListBlocksHTML()` with `showDraw=true` to also surface mL/units for prepping a syringe — the printed Schedule passes `showDraw=false` to stay uncluttered on paper.
- **Labels** need an exact `width x height` in mm matching the physical roll (Settings → label design, default 40×20mm). Since `@page` can't be scoped by selector, `printLabels()` writes the page size directly into the empty `<style id="labelPageStyle">` tag in `index.html` right before calling `print()` (and `printSchedule()` clears that same tag first, so leftover label sizing never leaks onto a schedule printout).

Label content isn't a separately-stored entity — `labelCandidates()` derives one label per (peptide, subject) pair by scanning `protocols` for that combination, plus a generic peptide-only candidate for any peptide with no protocol yet (for labeling bulk/shared stock). The Labels tab lets the user check which candidates to print and set a quantity (for printing N copies of one vial's label). `labelBoxHTML()` optionally renders a global logo image (`settings.logoDataUrl`, uploaded in Settings and downscaled client-side via `handleLogoUpload()` before being stored as a data URL) in the label's header row alongside the peptide name; `print.css` forces it grayscale since the NIIMBOT M2 is a monochrome thermal printer.

### Consumption report
The Reports tab answers "how much of each substance was taken over a date range." `consumptionReport(fromDateStr, toDateStr, subjectIds)` filters `doseLogs` by date and subject, then for each log splits it into components via `Calc.blendComponentDoses()` if its peptide `isBlend`, otherwise takes the logged mg as-is, and buckets the result by substance **name** (lowercased), not peptide id. That's the key design choice: a blend dose's component share and a standalone peptide of the same name land in the same bucket, so the report reflects true total-per-substance consumption regardless of whether it was taken alone or as part of a blend — at the cost of being a plain string match (a typo'd or differently-cased component name would bucket separately). Printing reuses the same container/print-mode mechanism as Schedule/Labels: `buildReportHTML(forPrint)` renders into `#printReportArea`, and `printReport()` clears `#labelPageStyle` first (same as `printSchedule()`) so no leftover label sizing leaks onto it — the report uses the default `@page` rule, same as the schedule. `forPrint` only adds the print date; this view is read in the browser far more than it's printed, which is also why the range presets (`reportRangePresets()`) exist.

Two things about the table are load-bearing rather than cosmetic. Each row carries a `via <blend>` note built from the entry's `sources` set, because a row like "KPV 36mg" is otherwise unexplainable when no KPV was ever bought — it arrived inside KLOW, and the name-bucketing above is what makes that invisible. And the per-row **Doses** count is doses *containing* that substance, so one blend dose is counted once per component and the column deliberately does not sum to the total; the honest figure is the "N doses logged" in the subtitle, which is why it lives there rather than in a footer cell that would read as a broken sum.

## NIIMBOT M2 integration
There's no direct printer integration/protocol code, and there are two ways a label actually reaches the printer:

1. **Browser print dialog** (`printLabels()`), if the M2 is registered as a normal PC printer via its driver — the exact-mm `@page` sizing above is what makes that work without a PDF library or clipping.
2. **PNG export** (`downloadLabelPNG()` / the Labels tab's "Download PNGs" button), for the NIIMBOT desktop app, which is the path that works without a macOS driver: the label is rasterized and imported into the NIIMBOT app's own canvas.

The PNG path has three constraints the DOM/print path doesn't, all handled in `renderLabelCanvas()` and `pngWithDensity()`:
- **Physical size has to be declared.** `canvas.toBlob()` writes a PNG with no `pHYs` chunk, i.e. no physical size at all, so the NIIMBOT app falls back to its own assumed density and the image lands undersized on the label — the user then stretches it by hand, which is what was costing resolution. `pngWithDensity()` rewrites the blob with a `pHYs` chunk (hand-built with a CRC32, no library) stating the real density, so a dpi-aware importer places it 1:1.
- **The export dpi is not the print head's dpi.** `settings.labelExportDpi` (default `LABEL_EXPORT_DPI_DEFAULT` = 406, i.e. 16px/mm) matches the density the NIIMBOT Mac app appears to lay imports out at — measured, not documented: a 480px-wide PNG landed at roughly ¾ of a 40mm label. It's a user-editable number in Settings → Label design (with the calibration formula shown inline) precisely because it's an observation about one version of their app. `LABEL_HEAD_DPI` (300 on the M2_H; the non-H M2 is 203) is separate and informational — it's the ceiling on what can reach paper, not what the file should be exported at.
- **No mid-tones.** The head is 1-bit thermal, so any grey — the muted text colour, the subject's accent colour, the pale border — gets error-diffusion dithered into visible speckle. The canvas export therefore draws everything in `LABEL_INK` (pure black on white) and relies on size/weight for hierarchy. The on-screen `.label-box` and the browser-print path deliberately keep the subject colour; only the rasterized export is forced monochrome.

Where the exported files land is also part of that path, and `labelSaveMode()` picks between three routes in preference order — the Labels tab's button label, the destination shown beside it, and the hint under it all describe whichever one is live:

- **`server`** (server.py running *and* `settings.labelSaveDir` non-empty): the PNGs are base64'd and POSTed to `/api/labels`, which writes them into that folder. This is preferred because it's the only route that works in every browser and needs no dialog at all — the folder is a path in Settings → Label design, so a repeat export is one click. Safari and Firefox have no `showDirectoryPicker` whatsoever, so without this they can only ever drop exports in `~/Downloads`.
- **`picker`** (no server, but the browser has the File System Access API): `showDirectoryPicker`/`showSaveFilePicker` ask for a real folder. The chosen `FileSystemDirectoryHandle` deliberately isn't in `state` — handles aren't JSON-serialisable — so the module-level `labelSaveDir` is session-scoped and one pick covers every export until reload (Chromium reopens the picker at the last folder via the picker's `id`). Note the API also needs a secure context, so this route is dead on a `file://` double-click. A cancelled picker throws `AbortError` and is a silent no-op, not a fallback to downloading.
- **`download`**: the original `<a download>` behaviour.

Anything that goes wrong on the server route (unwritable path, bad payload) reports the server's own error message in the Labels tab and then falls back to downloading, so an export is never silently lost.

`POST /api/labels` takes `{dir, files: [{name, data}]}` with `data` base64. It expands `~`, creates the folder if needed, and reduces every `name` to a bare basename that must end in `.png` — so a payload can only ever create label files inside the folder it names, never traverse out of it or clobber something else.

Exported files are named `<peptide>-<dose>.png` (`retatrutide-3mg.png`) by `labelFileName()`, using the same `Calc.doseMgOnDate` lookup the label itself prints, so the filename always matches what's on the label; a candidate with no protocol is just `<peptide>.png`. Writing through a directory handle overwrites a same-named file in place rather than appending " (1)" the way a browser download would — intentional, so re-exporting after a dose change replaces that label. `resolveLabelFileNames()` guards the one case where that would lose a file: two selected labels reducing to the same peptide+dose get the subject name appended, and only those.

If direct Bluetooth printing from a script is ever wanted instead, the community `niimprint` project would be the starting point, but M2 support there is unverified as of when this was written.
